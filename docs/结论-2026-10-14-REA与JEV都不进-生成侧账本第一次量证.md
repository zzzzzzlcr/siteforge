# 结论（2026-10-14）：REA 与 JEV 都**不进**生产 —— 以及生成侧账本第一次全量量证

**一句话**：两个外部工具都判**不进**；账本量出来，我们的瓶颈在**生成/修复期（占真失败 84%）**，
不在重放期 —— 而这两个工具想挂的、以及所有「让执行器更聪明」的方案，挂的都是那 **16%**。

⚠️ **数会漂**：8099 那本 `checkpoints.sqlite` 是**活的**（服务在写）。下面所有数字是
**2026-10-14 10:2x 的快照**。要重量：`python3 tools/fam_report.py --root runtime`。

---

## 一、REA：不进（沿用 10-13 的判，今天补一条）

10-13 那份 spike 已经判 **B 档**（有新证据、没改善修复），理由与三条实测边界见
记忆 `rea-spike-verdict.md`（只认回环 CDP / 只看顶层来源、跨域 iframe 抓不到 / 要 Node）。
今天补的是一条**新的否定证据**：

- 当时的候选挂载点是 `agent/graph.py:1469` 的 `deps.evidence_run`，它只可能补
  **「站方校验拒绝」**那一族（从页面 JS 里抽 `/api/validate-phone` 这类端点）。
- **生成侧账本里这一族是 0 趟** —— 生成侧根本走不到「提交给站方」那一步：
  分不开页死在**写 py 之前**、自测挂在**我们自己的浏览器里**、探路死在**没走到成功页**。
- 生产侧**确实有**这一族（见 §三 `submit_rejected_1/2`），但那是**已交付的 py**
  在生产 worker 上跑的事 —— 与「把 REA 挂进生成流程」不是同一件事。

⇒ **REA 对交付率的提升上限 = 0。** 它不是没用，是**救不到我们卡的地方**。

### 补记（2026-10-14 下午）：它的「靶子是空的」—— 以及 L1/L2/L3

后来有人提了更好的用法：**别在失败后拿它做诊断，把它升级成「生成期的技术分析层」**
（CDP 探路 → REA 分析相关 JS → 生成带技术约束的 Python）。这个方向本身站得住。
**但它给的三类优先样本，两类已修、一类已关门**：

| 它说优先测 | 现状 |
|---|---|
| **动态 ID / 无名选项**（`id="option-1728392"` 那种） | **已修** —— `1d0ddd4`：`_stable_first` 把「以 `-数字` 结尾的 id」贬到兜底 + `_target_of` 记 `label`/`nearby_text`（**认人**）。真站验收 `resolved_by=role+nearby_text` |
| **日期控件输入失败** | **已修** —— 10-12：`缺陷单-2026-10-12-生日框填不进去-日期框不吃insertText.md` + cdp 侧 native setter + 回读 |
| **表单下一步状态判断不准** | **已关门** —— 「判据分不开页」，最后一例 10-09、去重后 6 个站 |

⚠️ **而且那个动态-ID 的例子，仓里选的解法跟提案相反**：提案要 `[id^="option-"]`（前缀选择器）；
仓里**有意没走**那条（`lint.py:479` 把它从硬闸里撤掉），改走「**认人**」——
理由正是提案自己写的那句：「不能因为前缀匹配就直接点击，必须结合题目范围、选项身份，
并验证匹配唯一且可操作」。前缀会匹配多颗，唯一性验不出来就不敢点。

**它框架里最有价值的是 §五 的 L1 / L2 / L3 分层**，而且它诚实：
**L1（识别技术栈）已验**（49 段脚本 / 65.1 万 AST 节点）、**L2（定位控件实现逻辑）没验**、
**L3（推导稳定 Python 操作）没验**。**决定 REA 值不值的是 L2/L3**，不是 L1。

⇒ **结论不变，但理由要写准**：不是「REA 没用」，是**它现在没有靶子**。
它 §三 说能指导的那几类（弹窗状态控制、异步网络请求、前端路由转换、前端校验分支）——
**一条条对回去，全落在已关门的族里**。哪天冒出新族（比如「探路没走完」里有一块是
「页面 JS 行为看不懂」），再谈。今天量过：那 11 趟是「没在正文里见到成功文案」8 +
「预算到顶」3，**都不是 JS 行为问题**。

## 二、JEV：不进 —— 题库只有 39 道

JEV（TypeSafe AI 的决策模型，不生成文本、只回带概率的结构化判定，三原语
`Choice`/`Score`/`Noul`）的定位是「**枚举候选 → 选一个**」，正对着我们 `_relocate`
那一格。所以它比 REA 更值得认真验。**验了，不行。**

**先说要紧的**：JEV 挂在**执行期**（产物里每步问一次）本身就是错的 ——
产物今天是**纯重放**（骨架 + 字面量 + cdp，**零模型调用**，扔到 worker 上就能跑）。
挂上去 = 新增**联网 / 限流 / API 可用性**三种失败模式，而且**收益不沉淀**
（这一趟选对了，下一趟还得再问）。所以真该验的是挂在**生成/自测期当一次裁判**、
把它挑中的候选**写进产物的候选顺序**（仓里已有的机制是 `_target_for_replay`）。

**题库（离线回放，题干与答案都在账本里）**

| | 8099 | 8100 |
|---|---|---|
| click/fill 步 | 1865 | 302 |
| 有答案（`result.selector`） | 1722 | 285 |
| 候选**只有 1 条**（没题可做） | 1343（72%） | 234 |
| **答案名次 = 0（现在这套顺序已经选对）** | **1686 / 1722 = 97.9%** | 282 / 285 = 98.9% |
| **答案名次 > 0（顺序可能有活干）** | **36 道** | 3 道 |

题干 = `target`（`text`/`role`/`near`）+ `target.selectors`；答案 = `result.selector`
（探路时**真发出去、也真成了**的那一条）；基线 = 现在这套顺序（"`selectors[0]` 试起、
第一个命中就停"）。

**39 道题 / 2007 步。而且这三个细节让它更小：**

1. **集中**：36 道分布在 14 单，`job-340832aaeeef` **一单占 15 道（42%）**。
2. **64% 的「正确答案」本身会漂**：36 道里 **23 道**，答案是
   `body:nth-of-type(1) > div:nth-of-type(3) > …` 那种长链 —— **JEV 选对了它下一趟照样漂**
   （`#input-167` → `#input-163` 那一族）。选对一个会漂的地址，等于没选。
3. **在最大的那一单上方向还是反的**：`job-340832aaeeef` 里被跳过的 `sel[0]`
   （`button.css-kiczul`）**不脆弱**，用了的反而是脆弱长链 —— 而且**被跳过的那些 0/36 脆弱、
   答案 23/36 脆弱**。所以这一单的病**不是「好地址被排在后面」**，是
   **「排第一的当时没命中、兜底的长链命中了」**：那是**探路那一刻的页面状态**问题，
   **排序再聪明也治不了**。

顺带：`result.match_count` **全部是 1** —— 不存在「选择器命中多个元素」那一类问题。

⇒ **JEV 离线回放不值得跑：天花板在题量，不在模型。**

⚠️ **边界**：这只否掉「**接进现有产物**」这条路。它**排除不了**「让 JEV 直接看页面选元素」
那种**另一套浏览器 Agent**（jev-browse 那类）—— 但那是**换产品**，得另算账。

## 三、生成侧账本：第一次全量量证

数据源：`runtime*/checkpoints.sqlite`（LangGraph 快照，`writes` 表 + msgpack）+
`runtime*/explore/<job>/attempt-*.jsonl`（探路账本）。工具：`tools/fam_report.py`。

### 3.1 三个口径 —— 缺一个就会读反

1. **人喊停不是失败**（`paused` / `human_stop`）：8099 那本账里 **占四成**；
   **窗口基建**（`no_window` / `window_gone`）也不是我们代码的病。两样都得剔掉再算。
2. **重试会灌水**：`getfixapro` 一个站 09-30 一天重试 **9 趟** ⇒ 那一族「17 趟」
   去重后只有 **6 个站**。所以每一族都要同时看**趟数**与**去重站数**。
3. **量不到不许当成 0**：没账本的趟、没诊断的趟、判不出 A/B 的趟 —— 各自出声。

### 3.2 数字（8099 运营，146 终局）

```
交付 29  ·  人喊停 + 窗口基建 74  ·  真失败 43
全量交付率 29/146 = 19.9%      跑到底 29/72 = 40.3%
```

| 探路没走完 | 11 | 8 | |

### 3.4 A 类 / B 类（全表唯一带判断的一格）

判据与 `agent/state.py` 的 `END_REPAIR_STUCK` 同一句话（「同一处、同一句话连着两次」），
**不另立尺子**。分母 = **修过两轮以上的 11 趟**（其余 134 趟一轮都没修过，这一格对它们是空的）。

```
A 原地反复                    5 趟 / 4 站
     Buy now · Next → · Your postcode · Accept All Cookies ×2
B 往前推进                    0 趟   ← 这是量到的 0
同一个抱怨、但没点名（不是页面元素）   6 趟 / 5 站
```

**⚠️ 步号（`failed_step`）不是判据 —— 这是量出来的**：修完会**重写整份 py，步号跟着重编号**。

| 真事 | 第 1 轮 | 第 2 轮 |
|---|---|---|
| `job-cedaca6eaa52` | 第 **4** 步 · 滚不动「Buy now」 | 第 **3** 步 · 没找到「Buy now」 |
| `job-d40bb4d2d2be` | 第 **19** 步 · 滚不动「Next →」 | 第 **16** 步 · 滚不动「Next →」 |
| `job-c053e0b049f3` | 第 **9** 步 · trace 没写为什么 | 第 **60** 步 · 一字未变 |

而且 `第 0 步` 满场都是（3 趟）—— 那是**没记到**，不是「第 0 步」。
判据只用**抱怨点名了哪个东西**（`「…」`里那几个）。第一版拿步号当判据，被这三条打回来了。

**「没点名」那 6 趟里 4 趟原文是「trace 里那一步没写为什么」** ——
那是**我们自己没记下来**。修 py 修不动是必然的：**诊断本身就缺料**。

### 3.5 A 还是 B？—— **B 是主瓶颈**（两份账本一致）

| | A：有 py 但跑不过（重放期） | B：生成/修复期就交不出去 |
|---|---|---|
| 8099 运营（真失败 43） | **7 趟 · 16.3%** | **36 趟 · 83.7%** |
| 8100 测试（真失败 14） | 2 趟 · 14.3% | 12 趟 · 85.7% |

B 的构成：判据分不开页 17 · 探路没走完 11 · 编译层 5 · lint 打回 2 · 缺线 1。

**⚠️ 但这要分两本账问，否则会读反：**

| 要优化的是 | 看哪本账 | 瓶颈 |
|---|---|---|
| **首次交付成功率** | 生成侧（上表） | **B，84%** |
| **交付之后的运行成功率** | **生产侧 FMR** | **100% 是 A** —— 能到那儿的都是**已交付的 py**（14 天 / 9 站 / 116 单） |

两本账分母不同、**不能相加**。而今天讨论的工具（REA、JEV）**都在 A 那一侧**。

## 五、下一步真正的两个问题

1. **B 那 84%**：判据分不开页（已关门）+ 探路没走完 11 + 编译层 5。
   **编译层是唯一 10-13 还在发生、且长在我们自己骨架上的族。**
2. **判据失效了，账上没留痕**：「trace 里那一步没写为什么」4 趟 ——
   我们连「为什么」都没记下来。**判据失效这件事本身没有反馈通道**，所以下一趟只能从头再来。

> 所以那份分析说的「下一代架构不是更强的 Browser Agent，而是能把探索/诊断/修复经验
> 持续编译成稳定 Python 的系统」——**方向对，但要补一句**：这个仓**已经是**那个结构
> （L1：`_POPUP_HOOKS`/`_consent_click_like`/`_not_load_bearing_clicks`/`_stable_first`；
> L2：`_relocate`/`_target_for_replay`/`late_element`；L3：`diagnose → draft` + `hints` + 人），
> **缺的不是那一层，是「知道那一层在哪一页上失效了」**。
> 证据：A 类那 5 趟里，「Accept All Cookies」那两趟正是 `_POPUP_HOOKS` 管着的形状 ——
> **钩子表在跑，却没认出那一页的按钮**，而它的判据是**有意**收窄的
> （「宁可漏，不可误标」）。**判据失效，账上不留痕。**
